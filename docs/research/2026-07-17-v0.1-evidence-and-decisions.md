### Production atomic-exchange dependency decision

Tree's bounded 2026-08-21 trial explicitly reverses the prior assertion that
standard-library filesystem primitives are sufficient for every publication
path. The production dependency is exactly
`rustix = { version = "=1.1.4", features = ["fs"] }`. Provenance is the Cargo
registry package sealed by `Cargo.lock`, from the Bytecode Alliance `rustix`
repository. Its manifest declares Rust 1.63 compatibility and the license
expression `Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`, all below the
repository's pinned Rust 1.97.1 toolchain and subject to the routed audit, deny,
license, source, duplicate-version, and SBOM gates.

The justified production surface is the following bounded set of safe rustix
filesystem APIs and supporting types:

- `rustix::fs::open` opens the already-confined project root directory;
  `rustix::fs::openat` then opens or exclusively creates the validated one-leaf
  entries relative to held root or transaction directory descriptors. Those
  entries include Fresh-Create pending instructions, original/reviewed/exchange
  witnesses, their final pre-exchange durability reopens, recognized recovery
  leaves, and staged completion receipts. `Mode` supplies restrictive creation modes.
  `OFlags` supplies `RDONLY` or `WRONLY`, `DIRECTORY`, `CREATE`, `EXCL`,
  `NOFOLLOW`, `CLOEXEC`, and `NONBLOCK` as applicable. `NOFOLLOW` and descriptor
  anchoring reject final-component symlinks; `NONBLOCK` prevents a recognized
  special-file leaf from blocking the worker while metadata is inspected, but
  does not admit it: every leaf must be a bounded regular file before read or
  sync.
- `rustix::fs::Dir::read_from` and its `DirEntry` results enumerate only the
  opened transaction-directory descriptor. Names are treated as untrusted,
  compared with the closed versioned witness set, and never reinterpreted as
  multi-component paths. The same bounded authority now preflights the complete
  four-leaf staging set before a pre-exchange abort removes any witness.
- `rustix::fs::renameat_with` with `RenameFlags::EXCHANGE` atomically exchanges
  the validated `AGENTS.md` and `exchange` leaf names under their opened parent
  descriptors. Rustix maps this to Linux `RENAME_EXCHANGE` and macOS
  `RENAME_SWAP`; no ordinary-rename fallback is permitted.
- `rustix::fs::linkat` with empty `AtFlags` publishes the completion receipt
  create-only from its transaction leaf to its validated root leaf. The
  subsequent identity, link-count, content, mode, and durability checks remain
  part of the receipt authority; the hard link alone does not establish
  completion.
- `rustix::fs::unlinkat` with empty `AtFlags` removes verified regular witness
  leaves and replaces an incomplete, independently linked staged completion
  receipt only after its identity and link count authorize repair. It also owns
  descriptor-anchored pre-exchange abort cleanup after the closed-set preflight;
  no pathname removal fallback exists. `unlinkat`
  with `AtFlags::REMOVEDIR` removes the verified empty transaction directory.
  Cleanup calls occur only after the versioned recovery matrix authorizes them;
  an unknown entry or failed removal retains evidence and fails closed.
- `rustix::io::Errno` distinguishes only the expected `EXIST` collision during
  create-only completion staging, which triggers full existing-receipt
  validation, from other errors; `IO` is also used for deterministic failure
  injection. No errno authorizes an unvalidated retry or fallback.

These APIs and flags are available through rustix on the supported Linux and
macOS targets. Atomic exchange retains its platform-specific semantics above;
the remaining calls use the common Unix descriptor-relative filesystem model.
Every pathname argument is either an already-confined project root or a
validated relative leaf beneath an opened and identity-checked directory
descriptor. Unsupported target, syscall, kernel, filesystem, cross-device, leaf
type, identity, or durability state fails closed; after a possible publication
effect it is classified as ambiguous and recovery evidence is retained. This
inventory does not add Windows or other platform support.

Research Run therefore keeps `unsafe_code = "forbid"` rather than adding raw
`libc` syscall code. The enabled dependency surface is the `fs` feature plus
rustix's default `std` feature. Its locked platform closure adds `errno` and
`linux-raw-sys` where applicable. It adds no service, network client, telemetry,
database, runtime thread, or external write. The attack surface is the pinned
safe wrapper and its platform bindings around the enumerated local filesystem
operations; descriptor-relative access, closed leaf names, symlink rejection,
regular-file checks, creation exclusivity, and fail-closed errno handling bound
untrusted influence to the selected local workspace transaction.

The build cost is compiling and linking the pinned filesystem abstraction and
its target-specific closure. Maintenance includes tracking this exact API and
flag inventory across the pinned rustix version, both target implementations,
the lockfile, and the routed audit, deny, license, source, duplicate-version, and
SBOM gates; any authority-path API drift requires this decision to be updated.
The append runtime cost is descriptor opens and enumeration, one exchange
syscall, create-only receipt linking, authorized cleanup, three independently
stored instruction witnesses bounded to 1 MiB each plus small version and
completion records, metadata checks, and deliberate file/directory syncs. That
cost buys continuous canonical-path binding and a crash-recoverable exact
pre/post matrix.

Standard-library path-based directory access cannot supply the complete
fd-relative, no-follow, atomic-exchange authority used here. Standard-library
double rename, move/link, and hard-link publication were rejected because they
expose an absence or lost-update window. Raw platform syscalls were rejected
because they require project-owned unsafe code and two target-specific
implementations; Linux-only `openat2` cannot satisfy the macOS contract. Adding
a broader capability-filesystem crate would add another production dependency
without removing the exchange requirement, and an external helper would weaken
package and runtime closure.

Unsupported targets fail before transaction effects. An unsupported kernel or
filesystem, cross-device state, syscall failure, special-file witness, or
uncertain prior effect has no ordinary-rename fallback and retains transaction
evidence as ambiguous. The
claim is exact bytes plus Unix mode on supported Linux and macOS filesystems. It
does not cover ownership, timestamps, xattrs, ACLs, every uncooperative direct
writer, or mutation through an already-open file descriptor. Rollback removes
the dependency and all enumerated rustix-backed authority paths, then withholds
append integration on existing instruction files; it must not restore the old
non-atomic algorithm or substitute path-based cleanup. No canonical JSON
migration is needed, and any retained versioned or legacy transaction remains
explicit until inspected under the matching implementation.

### Linux setgid transaction-directory compatibility decision

The Linux [`mkdir(2)` contract](https://man7.org/linux/man-pages/man2/mkdir.2.html)
states both that ordinary access permissions are derived from the requested mode
and umask and that a new directory inherits `S_ISGID` from a setgid parent. The
previous post-create check treated every bit outside `0700` as broadened access,
so a correctly requested private transaction could be created as `02700`, then
rejected before witness staging. That left an empty transaction which recovery
correctly retained as ambiguous, but made Append unavailable in a common shared-
project layout.

The repair distinguishes the least-significant nine access bits from special
mode bits. It continues to require a directory with no group/other access and
accepts only zero special bits, except on Linux where `S_ISGID` alone is accepted
when a pre-create parent snapshot was setgid and the child numeric GID matches
that snapshot. Setuid, sticky, combined or unexplained special bits, GID mismatch,
and non-directories fail closed. macOS remains strict because this slice has no
executed authority for child-directory `S_ISGID` inheritance there.

Research Run does not clear the inherited bit: `02700` grants the same access as
`0700`, while clearing it would add chmod, sync, and crash states and change group
inheritance without improving confidentiality. The parent snapshot is an
inherited-mode consistency guard, not a time-of-check/time-of-use proof; supported
CLI writers remain serialized and uncooperative path replacement stays outside
the product claim. A crash after directory creation but before the first plan-
bound witness may still leave an empty transaction, which recovery must retain as
`AmbiguousEffect`. The claim remains exact instruction bytes plus numeric Unix
mode, not ownership, GID custody, ACLs, xattrs, or universal writer safety.

### Development-only JSON Schema evaluator decision

The pinned `jsonschema` 0.33.0 crate is accepted only as a development
dependency. Its provenance is the Cargo registry package resolved by the
committed lockfile; the package declares an MIT license. It receives only
repository-owned schemas and fixtures during tests, never workspace or network

and command-line interface are excluded. This keeps the new attack surface and
build cost outside production while still adding a comparatively large test

continue to pass the routed dependency checks.

The justified benefit is executable Draft 2020-12 contract proof: fixtures now
exercise cross-field conditionals and referenced resources that structural key
inspection cannot validate. Alternatives were rejected for the current slice:
hand-written assertions duplicate the Rust validator without testing published
schema semantics; invoking an external validator weakens hermetic and installed
developer workflows; implementing a schema evaluator is disproportionate and
security-sensitive. Maintenance is limited to the pinned dev version and the
focused schema test helpers. Rollback is to remove the crate and executable
fixtures together, restore structural-only checks, and explicitly lower the
schema claim ceiling; no production data or format migration would be needed.

## Product decision

Three plausible first products were compared:

1. **Evidence-ledger CLI and workspace.** A researcher records sources, claims,
   evidence relationships, experiments, and current limits in a deterministic
   local format.
2. **Agent-ready project scaffolder.** A generator installs research-oriented
   contracts, folders, and checks into a new repository.
3. **Autonomous research orchestrator.** An agent plans searches and experiments,
   updates state, and coordinates research workflows.

Choose option 1. It provides direct researcher value without an AI provider,
turns the strongest Nathan-project practices into a reusable product, and creates
the typed state that future scaffolding or agents would need. Option 2 without a
working state model would ship ceremony. Option 3 would add trust, integration,
and evaluation burdens before the underlying evidence authority is proven.

The primary user is one graduate researcher or research engineer maintaining a
small, changing body of evidence. The first job is not "manage all research." It
is: **show me what we currently know, why we think it, what failed or remains
ambiguous, and what deserves attention next.**

## Canonical domain boundary

The implementation may refine names, but it must preserve these semantic roles:

- `ProjectManifest`: format version, project identity, and declared roots.
- `SourceRecord`: stable identity, citation or locator, provenance, and bounded
  notes. A source is not evidence for every claim by association.
- `ClaimRecord`: stable identity, exact claim text, scope, and human ownership.
- `EvidenceLink`: a typed relationship from a source, experiment, or artifact to
  one claim with a stance such as supports, limits, contradicts, or context, plus
  the specific evidence used.
- `ExperimentReceipt`: question, method or protocol reference, observations,
  interpretation, limitations, outcome, and next move. Negative and ambiguous
  outcomes are ordinary valid records.
- `ArtifactPointer`: workspace-safe or external locator, description, provenance,
  and optional digest. It is not an instruction to copy raw data.
- `ReviewDecision`: explicit human decision and rationale that may change the
  workspace assessment of a claim. AI authorship remains provenance, never
  authority.

Claim assessment is derived, not freely written. At minimum, deterministic status
must distinguish unsupported, limited, supported, contradicted, and unreviewed
states. Evidence links, generated prose, projections, retry, or file order cannot
silently promote a claim. "Supported" means supported within the declared
workspace evidence and review scope, not scientifically true in general.

Canonical records are the authority. Human and JSON status, indexes, context
packets, receipts, and summaries are projections that can be rebuilt. Publication
must be atomic and workspace-confined; an ambiguous prior effect must be inspected
before retry.

## Acceptance and truth policy

The final task must map every requirement to current evidence. A source review
does not prove code. Code does not prove packaging. Unit tests do not prove the
public journey. A local binary does not prove GitHub or CI state. A pull request
does not prove release or adoption. A self-authored technical review may find
defects, but it does not prove external validation or real-world usefulness.

The product can claim v0.1 readiness only when the clean-clone journey and
representative valid, invalid, interruption, retry, path, symlink, malformed
input, unsupported-promotion, redaction, packaging, and secret-scan cases pass on
the integrated tree. Real-world usefulness and scientific impact remain withheld
until researchers use the tool on real projects and return evidence.

## 2026-08-20 agent-integration claim boundary

The canonical contribution protocol and project agent readiness are separate
states. A workspace may contain valid protocol and record JSON while the active
root project instruction chain lacks the retrieve, classify, typed append,
validate, and handoff contract. Structural ledger validation alone therefore
cannot establish that an agent received or followed the protocol. The
validation v2 projection reports ledger validity and readiness separately: an
unavailable instruction inspection leaves a structurally valid ledger valid and
marks readiness unavailable. The published validation v1 schema remains the
unchanged legacy projection and does not describe v2 output.

The supported repair surface is an explicit digest-bound plan/apply/status flow
for the active root `AGENTS.override.md` or `AGENTS.md`. It may prove exact
manifest and protocol binding, preservation of existing instruction bytes,
conflict and drift detection, confined and symlink-safe publication, identical
retry, representative typed contribution, actual validation output, and v2
handoff. Handoff v2 binds one locked snapshot's validation result and authority
identity to its bounded context; v1 inspection remains compatible. Because
agent instruction discovery happens at run start, a successful apply establishes
readiness only for a newly started run/session. Current-run loading remains
unverified.

Append publication stages independent durable version, original `O`, reviewed
`P`, and exchange=`P` witnesses in a same-directory transaction. Linux and
macOS publication atomically exchanges the transaction leaf and canonical
instruction leaf through opened directory descriptors, so the canonical name
does not become absent. A change immediately before exchange is preserved in the
exchange slot and makes verification ambiguous rather than being silently lost.
The canonical and exchanged leaves are individually synced after exchange.
Before removing any witness, publication stages and syncs a bounded versioned
completion record inside the transaction, links it create-only into the opened
root, and syncs the linked file plus root directory. Recovery re-durabilizes this
plan-, byte-, mode-, target-, and transaction-bound record before resuming a
partial cleanup. Without that record, recovery accepts only exact full versioned
`canonical=O/exchange=P` or `canonical=P/exchange=O` states with matching plan,
bytes, identities, and Unix mode. Legacy, malformed, impossible, unsupported,
and uncertain layouts remain explicitly retained; there is no rollback or
non-atomic canonical-publication fallback. Post-publication cleanup failures are
ambiguous because the canonical effect is committed even when cleanup durability
requires an identical retry.

This boundary does not establish scientific truth, classify scientific content,
prove universal agent compliance, prevent every generic filesystem write, or
make an optional provider hook a security boundary. Signed-human-only claim
promotion and v1 handoff inspection compatibility remain unchanged.

### Final activation publication and proof-integrity decision

The last open-thread audit separated two misleading reports from the remaining
root defects. A valid durable completion receipt intentionally authorizes
partial or empty transaction cleanup. Witness removals are not required to be a
full pre-cleanup set: a crash before the transaction directory is synced may
persist any subset. Recovery therefore validates the receipt, canonical
reviewed bytes and Unix mode, every surviving recognized leaf, and the retained
hard-link identity before resuming cleanup. Requiring all witnesses—or an
assumed deletion suffix—would strand legitimate committed cleanup states.
Likewise, serialized Rust test execution is required by the global injection
harness and does not serialize threads created inside one test.

One real pre-exchange defect crossed the held-descriptor boundary. After opening
the project root and transaction directories, witness durability reopened four
leaves and both directories by pathname. Replacing the transaction pathname
with a same-shaped directory made the old sync return success; replacing it
with a symlink to a directory whose first witness was a FIFO blocked until the
five-second regression deadline. The repaired path verifies the relative
transaction anchor, opens each fixed witness leaf with fd-relative `openat`
using `NOFOLLOW`, `NONBLOCK`, and `CLOEXEC`, rejects non-regular leaves, syncs
the held transaction descriptor, rechecks the relative anchor, and syncs the
held root descriptor. It has no pathname fallback. This narrows avoidable
exposure to an uncooperative writer but does not claim universal protection
against such writers or writes through already-open descriptors.

The same audit made four proof contracts executable. Machine policy names all
five lifecycle witnesses, including `version`. The active ExecPlan distinguishes
historical PR #7 delivery from current PR #12 authority and requires execution
of every material changed boundary while allowing only precisely enumerated
defensive, unreachable, or low-value misses under the existing claim ceiling.
The installed read-only check fingerprints every entry's escaped relative path,
type, Unix mode, regular-file digest, and symlink target without following
links. Its self-test changes file mode, adds an empty directory, adds and
retargets a symlink, and replaces a file with a symlink. The installed v2 journey
runs `handoff inspect`, compares the embedded validation result with the actual
validation-v2 receipt, recomputes exact compact result and context digests, and
binds project, workspace, manifest, protocol, and instruction identities.

Finally, direct reproduction showed that the production crate did not compile
for `x86_64-pc-windows-gnu`: `rustix::fs` is unavailable on Windows and the
completion, receipt, staging-cleanup, directory, and atomic-exchange boundaries
were only partially gated. Complete Unix API gating plus pre-effect unsupported-
platform stubs now makes the production target compile while preserving Linux
and macOS as the only Append platforms. A dedicated CI compile check protects
that fail-closed boundary; it is not a Windows runtime or support claim. A
barrier-started same-workspace test also exercises two concurrent supported
apply attempts: exactly one publishes, the other observes either the held write
lock or installed no-op state, and the exact retry converges with no `.txn` or
`.done` residue.

These repairs prove descriptor-confined pre-exchange durability, representative
concurrent CLI authority, entry-complete installed read-only observation, and
complete installed validation-v2/handoff-v2 identity checks on their executed
platforms. They do not prove exact repository-wide coverage, Windows runtime
support, Product Fitness, universal agent compliance, scientific truth,
ownership, timestamps, xattrs, ACLs, or safety against every uncooperative
filesystem writer.

### Bounded transaction-directory enumeration decision

The exact-head security review after `86dcde589c21c0ce27baeee208b51b71921c5a28`
found that the project-root pending scan and staging-abort cleanup were bounded,
but both versioned transaction recovery and committed-completion recovery still
collected every directory child before enforcing their closed layout. A hostile
recognized `.txn` could therefore consume unbounded userspace iteration and
name memory while holding the workspace write lock.

The recovery review also separated a stale-root pre-effect check from the
excluded universal-writer claim. The atomic exchange used held descriptors but
did not compare the current project-root pathname with its held descriptor until
after the syscall. A deterministic fixture renamed the opened root, installed a
replacement root at the same pathname, and showed that the old implementation
exchanged inside the renamed root before returning ambiguity. The repair
revalidates project-root identity immediately before `renameat_with`; both roots
remain unchanged when the identity no longer matches. An uncooperative writer
can still race after that check, so the universal-writer exclusion remains.

The repair keeps the existing recovery authority and adds no dependency. Both
paths now stream directory entries. Versioned/legacy inspection accepts names
only from their closed union and retains no more than five; completion cleanup
accepts only the five lifecycle witness names. A non-UTF-8 or unknown name fails
immediately, and a sixth otherwise recognized name fails with the explicit
five-child budget. Public callers preserve the transaction and any durable
completion receipt as `AmbiguousEffect`. Deterministic regressions record the
old mixed-layout and six-name list failures, unchanged canonical bytes, and
retained evidence. The claim is bounded userspace enumeration and retained-name
memory; it is not a filesystem response-time guarantee.
