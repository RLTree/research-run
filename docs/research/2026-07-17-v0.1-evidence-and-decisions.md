### Production atomic-exchange dependency decision

Tree's bounded 2026-08-21 trial explicitly reverses the prior assertion that
standard-library filesystem primitives are sufficient for every publication
path. The production dependency is exactly
`rustix = { version = "=1.1.4", features = ["fs"] }`. Provenance is the Cargo
registry package sealed by `Cargo.lock`, from the Bytecode Alliance `rustix`
repository. Its manifest declares Rust 1.63 compatibility and the license
expression `Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`, all below the
repository's pinned Rust 1.97.1 toolchain and subject to the routed audit, deny,
license, source, duplicate-version, and SBOM gates.

The justified production surface is one safe descriptor-relative filesystem
operation: `rustix::fs::renameat_with` with `RenameFlags::EXCHANGE`. Rustix maps
that operation to Linux `RENAME_EXCHANGE` and macOS `RENAME_SWAP`, so Research
Run can keep `unsafe_code = "forbid"` rather than adding raw `libc` syscall code.
The enabled surface is the `fs` feature plus rustix's default `std` feature. Its
locked platform closure adds `errno` and `linux-raw-sys` where applicable. It
adds no service, network client, telemetry, database, runtime thread, or external
write; untrusted influence remains bounded to validated local workspace paths
and bytes.

The build cost is compiling and linking the pinned filesystem abstraction and
its target-specific closure. The append runtime cost is one exchange syscall,
three independently stored instruction witnesses bounded to 1 MiB each plus
small version and completion records, metadata checks, and deliberate
file/directory syncs. That
cost buys continuous canonical-path binding and a crash-recoverable exact
pre/post matrix. Standard-library double rename, move/link, and hard-link
publication were rejected because they expose an absence or lost-update window;
raw platform syscalls were rejected because they require project-owned unsafe
code; an external helper was rejected because it weakens package and runtime
closure.

Unsupported targets fail before transaction effects. An unsupported kernel or
filesystem, cross-device state, syscall failure, or uncertain prior effect has
no ordinary-rename fallback and retains transaction evidence as ambiguous. The
claim is exact bytes plus Unix mode on supported Linux and macOS filesystems. It
does not cover ownership, timestamps, xattrs, ACLs, every uncooperative direct
writer, or mutation through an already-open file descriptor. Rollback removes
the dependency and withholds append integration on existing instruction files;
it must not restore the old non-atomic algorithm. No canonical JSON migration is
needed, and any retained versioned or legacy transaction remains explicit until
inspected under the matching implementation.

### Development-only JSON Schema evaluator decision

The pinned `jsonschema` 0.33.0 crate is accepted only as a development
dependency. Its provenance is the Cargo registry package resolved by the
committed lockfile; the package declares an MIT license. It receives only
repository-owned schemas and fixtures during tests, never workspace or network
input in the shipped CLI. Default features are disabled, so its HTTP resolver
and command-line interface are excluded. This keeps the new attack surface and
build cost outside production while still adding a comparatively large test
dependency graph whose advisories, license metadata, and lockfile identity must
continue to pass the routed dependency checks.

The justified benefit is executable Draft 2020-12 contract proof: fixtures now
exercise cross-field conditionals and referenced resources that structural key
inspection cannot validate. Alternatives were rejected for the current slice:
hand-written assertions duplicate the Rust validator without testing published
schema semantics; invoking an external validator weakens hermetic and installed
developer workflows; implementing a schema evaluator is disproportionate and
security-sensitive. Maintenance is limited to the pinned dev version and the
focused schema test helpers. Rollback is to remove the crate and executable
fixtures together, restore structural-only checks, and explicitly lower the
schema claim ceiling; no production data or format migration would be needed.

## Product decision

Three plausible first products were compared:

1. **Evidence-ledger CLI and workspace.** A researcher records sources, claims,
   evidence relationships, experiments, and current limits in a deterministic
   local format.
2. **Agent-ready project scaffolder.** A generator installs research-oriented
   contracts, folders, and checks into a new repository.
3. **Autonomous research orchestrator.** An agent plans searches and experiments,
   updates state, and coordinates research workflows.

Choose option 1. It provides direct researcher value without an AI provider,
turns the strongest Nathan-project practices into a reusable product, and creates
the typed state that future scaffolding or agents would need. Option 2 without a
working state model would ship ceremony. Option 3 would add trust, integration,
and evaluation burdens before the underlying evidence authority is proven.

The primary user is one graduate researcher or research engineer maintaining a
small, changing body of evidence. The first job is not "manage all research." It
is: **show me what we currently know, why we think it, what failed or remains
ambiguous, and what deserves attention next.**

## Canonical domain boundary

The implementation may refine names, but it must preserve these semantic roles:

- `ProjectManifest`: format version, project identity, and declared roots.
- `SourceRecord`: stable identity, citation or locator, provenance, and bounded
  notes. A source is not evidence for every claim by association.
- `ClaimRecord`: stable identity, exact claim text, scope, and human ownership.
- `EvidenceLink`: a typed relationship from a source, experiment, or artifact to
  one claim with a stance such as supports, limits, contradicts, or context, plus
  the specific evidence used.
- `ExperimentReceipt`: question, method or protocol reference, observations,
  interpretation, limitations, outcome, and next move. Negative and ambiguous
  outcomes are ordinary valid records.
- `ArtifactPointer`: workspace-safe or external locator, description, provenance,
  and optional digest. It is not an instruction to copy raw data.
- `ReviewDecision`: explicit human decision and rationale that may change the
  workspace assessment of a claim. AI authorship remains provenance, never
  authority.

Claim assessment is derived, not freely written. At minimum, deterministic status
must distinguish unsupported, limited, supported, contradicted, and unreviewed
states. Evidence links, generated prose, projections, retry, or file order cannot
silently promote a claim. "Supported" means supported within the declared
workspace evidence and review scope, not scientifically true in general.

Canonical records are the authority. Human and JSON status, indexes, context
packets, receipts, and summaries are projections that can be rebuilt. Publication
must be atomic and workspace-confined; an ambiguous prior effect must be inspected
before retry.

## 2026-08-20 agent-integration claim boundary

The canonical contribution protocol and project agent readiness are separate
states. A workspace may contain valid protocol and record JSON while the active
root project instruction chain lacks the retrieve, classify, typed append,
validate, and handoff contract. Structural ledger validation alone therefore
cannot establish that an agent received or followed the protocol. The
validation v2 projection reports ledger validity and readiness separately: an
unavailable instruction inspection leaves a structurally valid ledger valid and
marks readiness unavailable. The published validation v1 schema remains the
unchanged legacy projection and does not describe v2 output.

The supported repair surface is an explicit digest-bound plan/apply/status flow
for the active root `AGENTS.override.md` or `AGENTS.md`. It may prove exact
manifest and protocol binding, preservation of existing instruction bytes,
conflict and drift detection, confined and symlink-safe publication, identical
retry, representative typed contribution, actual validation output, and v2
handoff. Handoff v2 binds one locked snapshot's validation result and authority
identity to its bounded context; v1 inspection remains compatible. Because
agent instruction discovery happens at run start, a successful apply establishes
readiness only for a newly started run/session. Current-run loading remains
unverified.

Append publication stages independent durable version, original `O`, reviewed
`P`, and exchange=`P` witnesses in a same-directory transaction. Linux and
macOS publication atomically exchanges the transaction leaf and canonical
instruction leaf through opened directory descriptors, so the canonical name
does not become absent. A change immediately before exchange is preserved in the
exchange slot and makes verification ambiguous rather than being silently lost.
The canonical and exchanged leaves are individually synced after exchange.
Before removing any witness, publication stages and syncs a bounded versioned
completion record inside the transaction, links it create-only into the opened
root, and syncs the linked file plus root directory. Recovery re-durabilizes this
plan-, byte-, mode-, target-, and transaction-bound record before resuming a
partial cleanup. Without that record, recovery accepts only exact full versioned
`canonical=O/exchange=P` or `canonical=P/exchange=O` states with matching plan,
bytes, identities, and Unix mode. Legacy, malformed, impossible, unsupported,
and uncertain layouts remain explicitly retained; there is no rollback or
non-atomic canonical-publication fallback. Post-publication cleanup failures are
ambiguous because the canonical effect is committed even when cleanup durability
requires an identical retry.

This boundary does not establish scientific truth, classify scientific content,
prove universal agent compliance, prevent every generic filesystem write, or
make an optional provider hook a security boundary. Signed-human-only claim
promotion and v1 handoff inspection compatibility remain unchanged.
